INTRODUCTION

This file describes the content of the tar file you have received. The
full data structure is inserted below.

At this stage, we are releasing data after completion of one SB (excuted
multiple times if required), so you will find only one member_ouss_id
directory.  This directory contains this README file and the following
directories: calibration, script, qa2, log, product.

- 'calibration' contains the files needed for calibration starting from
the initial ms to the fully calibrated data. 
- 'script' contains the reduction scripts used to process the initial ms
to calibrated data, but also to obtain concatenated data (if more than
one execution) and imaging products.  There are usually several scripts
dealing with different parts of the processing.
In case the calibration was done by the automated pipeline, you will
also see the Pipeline Processing Request File (PPR).
The most important script for you is the "scriptForPI.py". See the
section "How to restore the calibrated MeasurementSet (MS) for your data"
further below. (Note: the ALMA archive may prepend the script name
with the MOUS UID.)
- 'product' contains the fits files of the selected image products. 
These will not include all images of scientific value, but will indicate
the quality of the calibration and images.
- 'qa' contains the qa2 reports that show plots and text information
needed to assess the quality of the processing. In case the calibration 
was done by the automated pipeline, you will find the pipeline Weblog here.
- 'log' contains the CASA log files. 

For more information see also the "ALMA QA2 Data Products" document
and the "ALMA Technical Handbook" (in particular chapter 11 on the QA2 pass 
criteria) which are available for download from the ALMA Science Portal at 
https://almascience.nrao.edu/documents-and-tools

VLBI DATA

* Polarization calibration

The calibration of these Execution Blocks (EBs) has been performed by
combining different VLBI projects within the same VLBI Observing
Session. Such a combination was needed for a successful polarization
calibration of the VLBI observations. Hence, it is NOT possible for the
PI of this project to reproduce the polarization calibration tables
given in this package, since data not belonging to the PI's project
would be needed. The scripts provided in the package will apply the
proper calibration tables to the EBs owned by the PI (which are also
provided in this package), in order to produce optimum calibrated
visibilities for the ALMA data.

There are two subsets of observations in these ALMA data: the
"ALMA-mode" scans (observed with the phasing system OFF) and the
"APP-mode" scans (observed with the phasing system ON). The two modes
are not compatible, in terms of the polarization calibration. However,
both modes can be combined after the full-polarization calibration.
However, a poor parallactic-angle coverage of the polarization
calibrator in the ALMA-mode scans may degrade the ALMA-mode calibration
and make these data (much) worse than those of the APP-mode scans. In
those cases, for polarization calibration please use only the APP-mode
scans (which typically have a better parallactic-angle coverage of the
polarization calibrator).

* Flux scale error

The absolute flux-density scale has been derived from self-calibration
based on a primary flux-density calibrator (source Ganymede). Due to
some peculiarities of the APP data reduction, the System Temperatures of
the individual ALMA antennas (which would correct for second-order
opacity effects, related to the atmospheric mapping function at the time
of the observations of the primary flux calibrator) are not used in this
calibration. This introduces a *constant* amplitude bias factor (close
to unity within a few %) for each source. The amplitude calibration
provided in this package is the same as that of the ALMA-VLBI data,
which will be provided as a set of ANTAB (AIPS) tables generated by the
program PolConvert. This program is run by the VLBI correlators and,
besides generating the calibration information for ALMA, it transforms
the linear-polarization ALMA-VLBI data streams into a circular basis for
VLBI.

A complete description of the phase and amplitude calibration/conversion
of your ALMA-VLBI data with PolConvert can be found in:

Marti-Vidal et al. 2016, A&A, 587, 143

If the PI is interested in accounting for the second-order opacity
effects in these ALMA data, for a more precise absolute flux-density
calibration, please contact your ARC. (consider that the accuracy in the
absolute flux-density calibration at ALMA, of the order of 10%, is
likely worse than these second-order effects).

* Data quality

Any bad-quality data in these EBs will also likely affect VLBI data in
baselines to ALMA at similar times and frequencies (see the Reducer's
comments above). For a deeper assessment of the quality of these data
and their effects on the VLBI data, please contact your ARC. The
reducer's comments apply to the whole VLBI track, so it may refer to
scans that are not part of the data included in this package.

* Imaging of the calibrators

The "products" directory contains FITS images of all the sources
observed in the EBs of this project. Note that data from the entire VLBI
session (including additional EBs from other projects) have been used in
the imaging, for assessment purposes. For this reason, images that the
PI may get from the deconvolution of the data provided in this package
may have a higher thermal noise than the images stored in the "products"
directory. Since different projects share same calibrator sources, the
integration time per source in the entire VLBI session, may be longer
than the integration time in the PI's project. For more information,
please contact the VLBI scheduler of your project. In this package, only
the images (generated per spw) from the APP-mode scans have been
included.

HOW TO RESTORE THE CALIBRATED MEASUREMENTSET (MS) FOR YOUR DATA

In order to obtain your calibrated data from this package, you first need 
to obtain the raw data in ASDM format from the request handler or
other server where it is staged for you (see your notification email).

If you downloaded and untarred all available files for this delivery
as described in the notification email, then you will already see
(in addition to the directories shown in the tree listing above)
a directory "raw" containing your raw data in subdirectories
named "uid*.asdm.sdm" and no further action is necessary.

If you do not have a raw directory, you will need to download
and untar the tar balls of the raw data belonging to this delivery
and make sure they are put into the "raw" directory in your
"member_ouss_..." directory.

For the next step, you will need the right version of CASA to be
installed. Please find above the line starting with
"CASA version used for reduction:". The version indicated there
is what you need to use for running the scriptForPI. 

Once the raw data is in place, cd into directory "script", start
 
   casa --pipeline

and type

   execfile('scriptForPI.py')

(Note: the ALMA archive may prepend the script name with the MOUS UID 
as in member.uid___Axxx_Xxxx_Xxxx.scriptForPI.py . You will need to use 
that name then.)

(For some versions, CASA is released without pipeline.
If your CASA version is not one with the ALMA pipeline
included, the "--pipeline" switch is not available.
Check in the "script" directory of your delivery package to see
if it contains a file named "PPR*.xml".
If there is no such file, you will be able to run the calibration
without the pipeline.)

For more information on the execution of the pipeline please refer to
the ALMA Science Pipeline User's Guide available at
http://almascience.org/documents-and-tools/pipeline-documentation-archive

Running the scriptForPI will execute the entire calibration procedure 
and result in an MS or a set of MSs ready for imaging. 

In case the data was processed using the automated pipeline,
scriptForPI.py will produce the calibrated MS(s) by running the
"casa_piperestorescript" which applies the packaged calibration
and flagging tables (rather then regenerating them).

For projects that were imaged using the pipeline after April 2017, 
the scriptForPI will not split out the calibrated science SPWs into
uid_*.ms.split.cal .

If you only want the calibrated data, it is sufficient to stop here and
use the uid_*.ms, keeping in mind that the calibrated data is stored
in the CORRECTED data column, and all sources are in the MS.

If you want to run the imaging pipeline, you can start from here,
without changing the uid_*.ms.

If you want to force that scriptForPI.py performs the splitting-out
of the science SPWs, you need to edit or create the file 
*scriptForImaging.py (the ALMA archive might have prepended the name 
by the MOUS UID) and put at least one line into it that does _not_ 
contain "#" (the Python comment character). The scriptForPI will then 
regard this as a non-trivial imaging script and proceed with the splitting.

If the casa_piperestorescript is not available (as can be the case
for pipeline-calibrated TP datasets), the scriptForPI will instead 
run the entire calibration pipeline using the "casa_pipescript". 

You can force the execution of the casa_pipescript instead of
the casa_piperestorescript by moving the casa_piperestorescript.py 
out of the script directory. Rerunning the pipeline can be useful 
if you want to tweak its parameters. Otherwise the restore is faster.

The calibrated MS(s) can then be processed with "scriptForImaging.py".

The "scriptForImaging.py" may partially be interactive (for masking)
and should be executed by copy and paste.

For TP pipeline-calibrated MOUSs, the scriptForImaging.py is NOT provided. 
You are able to find all used sdimaging task parameters in the CASA logs 
for stage 13 in the weblog.   

The scriptForPI offers a "SPACESAVING" option to limit the disk space 
usage during and after its execution. In order to make use of this, 
the Python global variable SPACESAVING needs to be set before starting 
the script, e.g. using

  SPACESAVING = N
  execfile('scriptForPI.py')

where N is an integer from -1 to 3 with the following meaning:
SPACESAVING = 0 same as not set (all intermediate MSs are kept)
            = 1 do not keep intermediate MSs named *.ms.split
            = 2 do not keep intermediate MSs named *.ms and *.ms.split
            = 3 do not keep intermediate MSs named *.ms, *.ms.split,
                and *.ms.split.cal (if possible)
	    = -1 (minus one) do not check the available disk space

With SPACESAVING=0, the required additional diskspace is up to 14 times 
as large as the delivered data (products and rawdata) while with 
SPACESAVING=3 (maximum savings), it is up to 6 times as large. 
The script will estimate the required disk space and will not execute 
if there is not sufficient free space available.
